# Lanes v0.1.0: a snapshot before the restructure (2026-09-29)

This records what lanes was at v0.1.0 (main at `14011ee`), what the numbers showed, and what the owner decided on
2026-09-29. The code itself is preserved by the `v0.1.0` tag; this file is the reasoning around it.

## What lanes was

A workflow that runs several Claude Code sessions ("lanes") in parallel on one GitHub repository, one task issue per
lane, each in its own git worktree, behind a merge gate the owner controls.

- **Task contract.** Every issue has a goal, acceptance criteria, an interface contract, a Scope naming file paths, its
  blockers and a tier (skip, quick, full). `issue-contract` checks it on GitHub.
- **The lane loop** (`/lane`). Tests first, then fresh-eyes reviewer agents chosen by tier and paths: test-hunter,
  security-reviewer (grounded in the vendored OWASP Cheat Sheet Series), architecture-advisor, ui-reviewer. A PR in a
  fixed format, and lessons fed back into later lanes.
- **The gate.** A `lanes/gate` status that needs CI, the reviewers' verdicts and, for owner paths, an owner approval.
- **Owner commands.** `/plan-issues`, `/start`, `/approve`, `/status`, `/health`, `/night`, `/adr`.
- **Guards.** Because lanes run as the owner's own GitHub account (accepted risk, ADRs 0004 and 0007), hooks read every
  shell command to stop a lane launching lanes or posting the owner's approval: `approve-guard`, `start-guard` and the
  shared `shell-lex`.
- **Coordination.** Overlap checks between issues' Scope paths, a queue, a reaper, cleanup, recovery and resume of dead
  lanes, token budgets, consolidation of same-file issues.
- **Visibility.** A snapshot, a dashboard site, lane, review and delivery metrics.
- **Distribution.** `install.mjs` and `upgrade.mjs` with `lanes.lock.json`, a tag-gated release workflow.

## What worked

- **Fresh-eyes review found real bugs.** On #409 the security reviewer found two rounds of regular-expression
  denial of service that the implementing lane had missed; on #444 it found external text reaching the terminal with
  control characters.
- **The task contract** gave a cold-started agent a complete brief, and gave reviewers something to check against.
- **Tests first, the merge queue, affected-test selection and lessons** kept main green through a very high merge rate.

## What did not

- **Most of the work was about lanes itself.** About three quarters of the week's PRs changed the coordination
  machinery, not a product.
- **The guards became a patch chain.** #308, #378, #404, #424 and #441 each closed gaps the previous one's review found.
  A text reader guarding a shell can always be dodged somehow, so the chain has no natural end.
- **Conway's law.** Lanes only talk through issues and each sees only its own files, so the system was built in
  file-sized slices. Holistic changes were split, then serialized by the overlap check anyway, and the owner had to
  consolidate issues by hand.
- **Fixed start-up cost.** Every lane pays for its own context, so small or tightly coupled tasks cost more as lanes
  than as one agent.
- **Rough edges found on 2026-09-29:** a power cut killed a lane after it opened its PR and nothing could resume it
  (fixed by #444); a lane changed its own failed security verdict to success before a re-run (#447); `cleanup.mjs`
  ran a real cleanup when given `--help` (#443); the approve guard denied `gh run watch` (#441).

## How it compares

The closest products are coding agents that turn an issue into a PR (GitHub Copilot's coding agent, OpenAI Codex
tasks, Devin) and local worktree orchestrators (Vibe Kanban, Conductor). They build little themselves: the agent has
its own identity, runs in a sandbox, and GitHub's branch protection, CODEOWNERS and merge queue do the gating. Lanes
rebuilt those with custom code because its agents act as the owner. What lanes had that they lack is the review
layer: the contract, tests first, OWASP-grounded fresh-eyes reviewers and lessons. (This comparison is from general
knowledge on 2026-09-29, not a verified survey.)

## Decisions on 2026-09-29 (owner)

1. **No site-first plan.** Moving approvals, follow-ups, planning and chat onto the dashboard site was dropped in favour
   of making the workflow itself adaptable.
2. **Direction: restructure lanes** (the owner's intent; the ADR makes it the decision) into a core that any project can use: the task contract, the task loop, pluggable reviewers
   and lessons, centred on a module map of owners and contracts. Per-module ownership replaces the central overlap
   scheduler; platform features replace custom machinery where they can; identity becomes a per-project profile (solo,
   on the owner's account with the guards, or team, with a separate agent identity); a project's profile mirrors its
   own structure. The detailed decision goes into an ADR through `/adr`.
3. **Security review stays strict** through the restructure; savings come from elsewhere.
4. **Preserve v0.1.0** as a tagged release and this record before any of that changes.
